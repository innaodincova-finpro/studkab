# C-071: отдельное сохранение проверки и передача

Требования R3/R8/R9. База — main bc079269c68bc737cabe32bf590a7369b12d5cba,
после опубликованного C-070 / PR #111. Этот документ описывает пакет установки;
его наличие не означает установку или производственную приёмку.

## Что меняется для исполнителя

1. Открыть итоговую проверку, скачать точный Word, заполнить 16 пунктов и подтвердить получателя.
2. Нажать «Сохранить итоговую проверку». Студенту ничего не передаётся.
3. Окно можно закрыть или страницу перезагрузить: протокол и файл восстанавливаются с сервера.
4. Нажать отдельную кнопку «Передать студенту». Повторное открытие показывает подтверждённую передачу.

При потере ответа сначала обновляется состояние. Стабильный идентификатор передачи
равен версии файла. Изменение документа, паспорта или получателя требует новой
проверки. Ошибка сервера блокирует передачу, а не считается подтверждением.
Сохранённый протокол нельзя редактировать: изменения оформляются новой версией.

## Зависимости и порядок установки

Не объединять frontend раньше готовности SQL и Edge. Объединение в main запускает
существующее автоматическое развёртывание Edge; GitHub Pages обновляется отдельно.

1. Убедиться, что Safety checks этого PR прошли, включая SQL и replay миграций.
2. Сверить фактическую историю миграций с manifest.json. Не применять накопленные
   pending-миграции без сверки и не выполнять безусловный db push.
3. Установить только `20260919124300_result_review_context_guard.sql` при наличии
   его предыдущих зависимостей: версионные результаты, паспорта, review_statuses.
   Миграция одной транзакцией обновляет INSERT-триггер и добавляет читающий маркер
   `public.studkab_result_context_version()`. Для service_role он возвращает 1;
   anon/authenticated не получают права выполнения. Таблицы и записи не создаются
   и не удаляются, права чтения закрытых таблиц не расширяются.
4. Развернуть совместимый `studkab-requests`, затем frontend. Проверить успешность
   обоих заданий, опубликованные версии results-ui v10 / request-workflow v2 и
   service worker `studkab-v61-separate-result-review`.
5. На отдельной синтетической заявке проверить под исполнителем чтение
   `result-review-state`: none → prepared → reviewed → delivered. После сохранения
   проверки результат ещё отсутствует у тестового студента. После отдельной
   передачи студент скачивает байты с тем же SHA-256.
6. Повторить закрытие окна/перезагрузку, потерю ответа, смену паспорта/получателя;
   проверить отказ студенту в чтении протокола и отсутствие дублей передачи.
   Не менять заявки реальных студентов и не запускать платный AI.

Если SQL-маркер отсутствует, новый endpoint возвращает ошибку и новый клиент
закрывает передачу. Если новый endpoint ещё не установлен, клиент также не
считает проверку сохранённой. Это защита от промежуточного состояния, а не
замена правильному порядку установки.

## Совместимость и откат

Исторические документы без reviewContext остаются читаемыми и сохраняют прежний
контракт выдачи. Новый интерфейс не переиспользует их проверку как проверку новой
версии. Новые документы привязаны к утверждённому паспорту; INSERT-триггер проверяет
его под блокировкой заявки, согласованной с сохранением/утверждением паспорта.

Предпочтительный откат: вернуть frontend с новой версией cache, оставив совместимые
Edge и SQL-защиту. Не удалять версии, проверки и выдачи. Если необходим откат SQL,
сначала отключить новый маршрут; возврат старого триггера требует отдельного
проверенного изменения. Маркер нельзя оставлять включённым без соответствующей защиты.

## Границы доказательств

Локальные браузерные сценарии используют синтетические данные и mock endpoint.
PGlite проверяет настоящий SQL, но не заменяет конкурентную приёмку production.
Факты локальных и CI-проверок фиксируются в TRACEABILITY.md и PR. Рабочая приёмка
на двух тестовых аккаунтах, физический телефон и полный FIN-UAT-01 остаются
отдельными действиями. Пакет не закрывает целиком TASK.md.
