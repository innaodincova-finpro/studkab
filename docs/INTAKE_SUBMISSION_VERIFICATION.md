## Изменение приложения

Карточка → серверный snapshot/валидация → копии всех актуальных оригиналов в
прежний приватный request-bucket → одна транзакция submit + вложения + прежний
publish → неизменяемая квитанция. Stable source IDs/path/hash позволяют безопасно
повторить загрузку после неизвестного транспортного исхода. До транзакции нет
заявки/уведомления. Копии после неудачного переноса не удаляются: это ограниченный
подготовленный комплект, пригодный для повтора; оригиналы и история остаются.

Сохраняется несколько файлов одной роли, несколько ролей одного файла — в
неизменяемом анализе. Все оригиналы становятся обычными вложениями с extracted_text
и связью intake_file_id. TXT-история остаётся; XLSX поддержан в destination bucket.
Прежний ручной upload всё ещё требует явной замены/материального цикла и не может
добавлять материалы после начала подготовки. Passport/Word/качество не одобряются.

Payload строится на сервере из анализа и точных ответов, не из присланной формы.
Однозначная дата ISO/DD.MM.YYYY нормализуется без придумывания. Неизвестные обязательные
сведения блокируют отправку по прежнему validatePayload; карточка объясняет только
конкретный недостаток. Контакт — подтверждённая почта аккаунта приложения.
Кандидаты требований и условия/ответы передаются в unverified черновик паспорта;
пропуск/понижение кандидата блокирует утверждение. Пределы 100 пунктов/2000 символов
текста/1000 символов источника не обходятся обрезанием: большой комплект получает
явный блокер. После изменения заявки исходный анализ помечается историческим.

UI хранит ссылку на отправляемый draft отдельно по аккаунту до запроса. Потерянный
ответ проверяется по квитанции. Закрытие/перезагрузка восстанавливает квитанцию и
одну связанную карточку работы без повторного submit. Новая заявка начинается явно.
В процессе отправки ввод/замена документов блокируются; другой аккаунт не видит
квитанцию, переадресованная/удалённая заявка не раскрывается прежнему владельцу.
