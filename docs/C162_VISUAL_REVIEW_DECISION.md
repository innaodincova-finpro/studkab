# C162 — как довести проверку Word до полной приёмки

Состояние на 28.09.2026: **решение для выбора интеграции**, не установленная
функция. Никакой реальный документ не передавался в новый сервис и новый
платный канал не запускался.

## Что проверяет текущая очередь

Supabase читает сохранённые байты DOCX и сверяет их SHA-256. Из архива
`word/document.xml` извлекаются абзацы основного текста. Текстовое задание,
методичка и паспорт подаются помощнику. Это позволяет искать содержательные
расхождения, но не доказывает отображение страниц, положение таблиц и рисунков,
колонтитулы, сноски, фактический объём или открытие в Microsoft Word.
C161 переносит замечания и отсутствие доказательств в протокол. C162 запрещает
текстовому отчёту утверждать `checked` для C11/C12/S02.

## Нужное доказательство

1. Получить с сервера **те же байты Word**, что будут доступны студенту;
   вычислить SHA-256, версию, ID утверждённого паспорта и получателя.
2. Доверенный преобразователь открывает этот DOCX и создаёт PDF/изображения
   всех страниц. Сохранить версию программы, хеш исходного Word и хеш PDF.
   Перемена Word/паспорта после преобразования делает результат устаревшим.
3. Проверяющий помощник получает страницы и извлечённый текст, сопоставляет
   видимые элементы с пунктами паспорта и заполняет по каждому коду
   `pass / fail / not_checked`, основание, страницу/фрагмент и метод проверки.
   Формат/объём сверяются с точными числовыми условиями, когда они имеются;
   отсутствующее в задании правило нельзя выдумывать.
4. Сервер заново проверяет идентичность Word, полный охват всех 16 пунктов,
   доказательства и отсутствие `fail/not_checked`. Одна модель не может
   удостоверять сама себя: детерминированные проверки размеров/страниц,
   сверка источников и расчётов остаются отдельными. Внешний PDF антиплагиата
   и оплата — отдельные шаги и лимиты.
5. Проверить на разных документах: сломанный DOCX, пропущенная страница,
   искажённые поля/таблица/рисунок, неверные расчёты, пустые источники,
   перемена паспорта и Word после проверки, ошибочный положительный ответ
   модели, отказ преобразователя и повтор после неизвестного платного вызова.
   Затем провести реальную приёмку от заявки до выдачи студенту.

## Вариант преобразования

Предпочтительный кандидат для проверки доступности — Microsoft Graph:
Microsoft документирует преобразование DOCX в PDF (`format=pdf`) через файл
в OneDrive. Нужны отдельная авторизация доступа к файлам, разрешение на
временное помещение студенческого Word в этот сервис, проверка удаления,
лимитов и фактических расходов. Даже успешное получение PDF не доказывает
редактирование в настольном Microsoft Word: C11 нельзя автоматически
отмечать как выполненный только по факту конвертации.

Проверка C163: для загрузки личному Microsoft-аккаунту достаточно
делегированного `Files.ReadWrite`; стандартный DELETE **перемещает в корзину**.
Для временного файла нужен `permanentDelete` по идентификатору, затем
подтверждение отсутствия файла. Microsoft перечисляет тарифицируемые Graph
API отдельно; преобразование DOCX→PDF в этом перечне не указано, но это не
подтверждает отсутствие платы за учётную запись, хранение или иной API.
Первоначальная попытка входа остановилась на сообщении «аккаунт с этим адресом
не найден». Позднее вход в личный OneDrive состоялся через защищённую форму,
но сервис показывает 5 из 5 ГБ и запрещает загрузку новых файлов.
Делегированный Graph-токен не настроен. Никакой файл не загружался; личные
файлы не удалялись и дополнительное место не приобреталось.

Другой кандидат — изолированный сервер с LibreOffice. Это новая инфраструктура
с размещением документов, поддержкой и расходами; она также не доказывает
идентичное отображение именно в Microsoft Word. Cloudflare Browser Run
создаёт PDF из HTML, а не открывает исходный DOCX, поэтому результат такого
рендера не доказывает оформление точного Word.

Локальная проба C164: `node scripts/render-word-pages.mjs INPUT.docx OUTPUT_DIR`
создаёт PDF, PNG всех страниц и манифест хешей в новом каталоге. На
синтетическом Word конвертер показал четыре страницы и таблицу на последней.
Это средство диагностики доверенных тестовых файлов, а не интеграция с
рабочей очередью; запуск на документах студентов без изоляции LibreOffice от
сети, учёта ссылок внутри DOCX, хранения и удаления файлов недопустим.
Манифест не подтверждает редактирование в Microsoft Word и не переводит
ни один из C11/C12/S02 в `pass`.

Проверка C165 уточнила маршрут ИИ: официально `deepseek-flash` принимает
PNG/JPEG как `image_url` в массиве `user.content`; каждый рисунок стоит до
1024 входных токенов. Но действующий `worker/ai-proxy.mjs` передаёт
`user` строкой, резерв считает текст, а URL/байты страниц в очередь не
поступают. Добавлен отдельный проверяемый контракт привязки
`visual-evidence.mjs`: тот же Word, тот же паспорт и получатель, все
страницы с хешами; он пока не вызывается рабочим сервером. Результат
конвертера остаётся недоверенным, пока не изолирован процесс и не доказано,
что эти изображения созданы из указанных байтов Word. Попытка проверить
изоляцию `bwrap --unshare-net` в текущей среде получила `Operation not
permitted`. Подключать визуальный платный запрос и объявлять проверку
оформления завершённой до решения этих ограничений нельзя.

Маршрут C166 для OneDrive написан только как серверный адаптер с макетными
HTTP-ответами: передача DOCX → сверка скачанного оригинала → PDF →
`permanentDelete` → проверка отсутствия по уникальному имени. Microsoft
Graph не вызывается без действующего делегированного `Files.ReadWrite`;
токен нельзя отправлять из браузера или фиксировать в репозитории. Загрузка
может завершиться при потерянном ответе: тогда объект ищется по имени и
удаляется без повторного PUT, а неизвестный исход блокирует результат.
Остановка серверного процесса между PUT и удалением обходит `finally`:
до внедрения требуется долговечный журнал временных файлов и очистка
после восстановления, плюс проверка фактического удаления в аккаунте.
Реальные Word и PDF пока не передавались и не конвертировались.

C167 добавил обязательный интерфейс долговечного журнала перед загрузкой и
операцию очистки после остановки процесса. При недоступном журнале новый PUT
не выполняется; восстановление не загружает Word повторно. Это ещё не
подключённый журнал в рабочей базе и не автоматическое восстановление:
проверено лишь на макетных ответах. Для рабочей интеграции нужны сохранение
записи в БД, отдельный повторяемый обработчик, действующий Microsoft-доступ,
реальная проверка удаления и рендер всех страниц PDF с контролем стоимости.

Источники для оценки возможности: Microsoft Graph
`https://learn.microsoft.com/en-us/graph/api/driveitem-get-content-format?view=graph-rest-1.0`;
загрузка `https://learn.microsoft.com/en-us/graph/api/driveitem-put-content?view=graph-rest-1.0`;
окончательное удаление `https://learn.microsoft.com/en-us/graph/api/driveitem-permanentdelete?view=graph-rest-1.0`;
перечень тарифицируемых API `https://learn.microsoft.com/en-us/graph/metered-api-list`;
Supabase Edge limits `https://supabase.com/docs/guides/functions/limits`;
Cloudflare Browser Run `https://developers.cloudflare.com/browser-run/how-to/pdf-generation/`.

## Условие следующего решения

До подключения преобразователя определить владельца учётной записи,
допустимость передачи документов студентов, нужные разрешения и бюджет.
Для C11 отдельно принять проверяемое определение: реальное открытие и
редактирование в Microsoft Word требует подтверждения именно этой операции;
если такого автоматического доказательства нет, C11 остаётся `not_checked`.
Нельзя ослаблять код или считать PDF эквивалентом настольного Word без явного
изменения требований и новой приёмки.
