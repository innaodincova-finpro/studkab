# C-080: повторная отправка заявки

Требования TASK R3/R9. Основание: подтверждённый путь повторной отправки возвращал
локальный `saved:true`, не отправляя поля на сервер. Файлы одной категории
накапливались, а реестр не обновлял уже импортированную заявку.

## Изменения
- Владелец читает исходный payload при открытии формы и отправляет update-request.
  Сервер валидирует поля, привязывает RPC к проверенной учётной записи и сравнивает
  исходный payload под блокировкой строки. Конфликт не перезаписывает данные.
- Номер и идентификатор остаются прежними. Предыдущий payload сохраняется отдельно.
- Замена файла указывает конкретный predecessor. SQL проверяет владельца, категорию,
  актуальность версии и отсутствие подготовки; два преемника невозможны.
  Старые файлы и извлечённый текст остаются неизменными. Контекст и проверка
  минимума источников используют только актуальные версии.
- Обновление реестра по revision сохраняет статус, заметку, дату и документ.
  Повторное чтение той же revision не затирает локальные правки исполнителя.
- Удаление заявки C-079 удаляет также новую историю payload. Общая история
  файлов ограничена 200 строками; текущих вложений не больше восьми.

## Явные границы
После создания паспорта или задания генерации студент получает отказ и предложение
согласовать изменение с исполнителем. Эта правка не реализует пересборку уже
утверждённого паспорта и не аннулирует исторические результаты.
Существующие неоднозначные категории с несколькими файлами не заменяются автоматически.
Повтор старой исторической версии файла не поддержан: нужна новая редакция.
Запись полей и загрузки файлов — отдельные операции. При ошибке загрузки форма
остаётся открытой без новой отметки об успешной отправке; сохранённые части не
удаляются, повтор загрузки тех же байтов идемпотентен. Это не атомарная пакетная отправка.
Telegram-уведомление создаётся для новой заявки; обновления видны по кнопке реестра.

## Установка и откат
До объединения необходимы Safety CI (включая SQL replay и browser) и review.
Сначала применить только новую SQL-миграцию, затем опубликовать studkab-requests
и studkab-generation-api (изменён общий source-minimum), затем frontend/Pages.
Автоматический deploy Edge на main не устанавливает SQL: порядок обеспечить до merge.
Не применять весь накопленный pending-список к рабочей базе вслепую.
После установки: тестовый студент меняет тему/автора и одно задание; исполнитель
обновляет реестр, видит прежний номер, новые поля и один актуальный файл категории.
Проверить второго студента, конкурирующую правку и отказ после паспорта.
Платные вызовы не нужны. Для отката вернуть frontend и Edge; SQL и историю сохранить.
Старый Edge видит историю файлов как общий список: при таком откате подготовку
приостановить, чтобы не смешать версии.

## Состояние
Изменения только в ветке. Рабочая база, Edge и сайт этим этапом не менялись.
Локальные Node/PGlite тесты отделены от CI и производственной приёмки.
