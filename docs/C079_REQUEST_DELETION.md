# C-079 — полное удаление неверной заявки

## Основание

Опубликованный реестр удалял только карточку из `D.items`. Серверная заявка,
вложения, паспорта, результаты и история подготовки продолжали существовать.
Стандартный `confirm()` также блокировал автоматизированную проверку интерфейса.

## Инварианты

1. Действие доступно только подтверждённому исполнителю.
2. Клиент передаёт точный ID дважды и явную причину удаления.
3. Подготовительный RPC блокирует новые вложения и до Storage проверяет, что все
   платные попытки сверены с неизменяемым финансовым журналом.
4. Физические объекты удаляются только через Storage API. SQL не удаляет строки
   `storage.objects` напрямую.
5. При сбое Storage заявка остаётся в состоянии удаления и повтор безопасен.
6. После Storage один закрытый service-role RPC удаляет граф заявки в правильном
   порядке и оставляет неперсональный журнал факта удаления.
7. Локальная/облачная карточка удаляется только после подтверждения сервера.

## Порядок установки

1. Применить `20260920111220_c079_request_deletion.sql`.
2. Опубликовать `studkab-requests` с новой операцией `delete-request`.
3. Опубликовать frontend и `sw.js`.
4. Проверить отказ студенту, отказ без точного ID, сбой Storage, повтор, заявку
   без серверной строки и полный синтетический граф.

## Откат

Frontend можно вернуть независимо: новый Edge остаётся обратно совместимым.
Edge можно вернуть после frontend. SQL-колонка, журнал и закрытые RPC additive;
их удаление при откате не требуется. Уже удалённые заявки не восстанавливаются.

## Границы доказательства

Локальные тесты не равны установке. Рабочие остатки не очищаются до успешного CI,
установки в указанном порядке и повторной проверки счётчиков.
