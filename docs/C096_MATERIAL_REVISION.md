# C096 — согласованное дополнение материалов

Статус: реализация и независимая проверка в отдельной рабочей ветке.
Установка в рабочую среду и пользовательская приёмка не выполнены.

## Причина

При открытии заявки автоматически создаётся проект паспорта. C080 запрещает
добавлять вложения при наличии любого паспорта, включая draft/stale. Поэтому
сообщение «согласуйте изменения с исполнителем» не имело исполнимого продолжения.
Отмена утверждения сама по себе не открывает загрузку.

Автоматический проект паспорта предусмотрен QUALITY_RELEASE_PLAN и сохраняется.
Изменение относится к R3/R8/R9 и M2/M3/M10, без новой инфраструктуры или оплаты.

## Ограниченный маршрут

1. Исполнитель указывает причину и открывает дополнение материалов.
2. Сервер допускает возврат только при отсутствии любых заданий генерации,
   сохранённых результатов и передач. Прежние паспорта становятся устаревшими.
3. Только автор заявки добавляет или заменяет файлы. Прежние редакции сохраняются.
4. Автор отдельно завершает дополнение по проверенной ревизии комплекта.
5. Исполнитель проверяет полный комплект и новую версию паспорта. Старое
   утверждение не восстанавливается автоматически.

Во время дополнения сервер запрещает утверждение, запуск подготовки и сохранение
результата. Гонки этих операций должны проверяться отдельными соединениями
PostgreSQL; последовательный PGlite-тест не заменяет такую проверку.

Независимая проверка выявила дополнительную гонку: открытый до возврата редактор
мог сохранить старые требования после завершения дополнения. Создание и утверждение
паспорта требуют ожидаемую ревизию материалов; после цикла сервер отклоняет старую
ревизию и отсутствие ревизии у старого клиента. Автоматический паспорт использует
ревизию того же прочитанного комплекта вложений, по которому рассчитан отпечаток.
Загрузка также привязана к конкретному циклу дополнения: задержанный файл из
старого окна не может попасть в повторно открытый цикл. Привязка проверяется
повторно в SQL непосредственно при записи, после загрузки байтов в Storage.

Текущая модель вложений — один актуальный файл каждой категории: задание,
методические указания, исходные данные, источники. Для наборов из нескольких
файлов нужна явная консолидация по категориям до загрузки.

## Разделение ответственности

- Серверный агент: SQL, API, проверки состояния и прав.
- Агент интерфейса: сценарии студента и исполнителя, восстановление после ошибок.
- Независимый проверяющий: изоляция, история, повторы и конкурентные операции.
- Ведущий: совместимость частей, общий набор проверок и фактический отчёт.

## Границы выпуска

Сначала миграция, затем Edge Functions, затем сайт. Установку нельзя считать
подтверждённой локальными тестами. После установки требуется полный цикл двух
ролей на одной синтетической заявке, затем повторение на остальных.

Откат интерфейса и API не должен удалять журнал, файлы, паспорта или защиту базы.
Открытый цикл дополнения при старом интерфейсе остаётся безопасно заблокированным
для подготовки до восстановления совместимой версии приложения.

## Параметр аутентификации при установке

Сверка 23.09.2026 обнаружила расхождение: рабочая функция `studkab-requests` v47
имеет `verify_jwt=true`, а `REQUEST_DELIVERY.md`, конфигурация и workflow задают
`false`. Действующее задание уведомлений передаёт отдельный `x-job-key` без
`Authorization`; обязательная проверка JWT на шлюзе несовместима с этим запросом.
В журнале HTTP есть ответы 401 без заголовка авторизации, но прямой привязки
каждого такого ответа к адресу функции нет; все эти ответы не приписываются
одному заданию.

Для установки предусмотрено восстановление `verify_jwt=false` с сохранением
существующей проверки внутри функции: браузерная сессия проверяется через Auth,
служебный запрос — сравнением отдельного секретного ключа. Отсутствующий или
неверный ключ не предоставляет доступ; новый способ аутентификации не вводится.
Перед публикацией нужно явно согласовать восстановление этого рабочего параметра
вместе с установкой C096. До такого решения рабочая функция и расписание не меняются.
После установки отдельно проверяются отказ без авторизации, отказ неверному
служебному ключу и фактическое выполнение предусмотренного задания уведомлений.
