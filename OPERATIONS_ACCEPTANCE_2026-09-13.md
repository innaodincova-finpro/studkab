Проверяемая версия: `e2da8670b0c8ca127fd4dea5abf5c4a2de4d4531` (main, PR #58).

Этот протокол разделяет фактическую проверку опубликованной системы, автоматические
проверки и действия, которые требуют отдельных устройств или независимых участников.

тестовому этапу, но не к массовому подключению реальных студентов.

## 6. Выявленные ограничения и риски

1. Нет фактического теста двух независимых студенческих аккаунтов на разных устройствах.
2. Нет полного восстановления Supabase из резервной копии в отдельной среде.
3. Нет проверки на физических iPhone и Android.
4. Нет полного маршрута реального уведомления с открытием правильной заявки.
5. Нет пилота с 2–3 независимыми тестовыми пользователями.
6. Supabase используется совместно со вторым приложением «Точка дня».
7. В общем проекте Supabase отключена проверка паролей по базе скомпрометированных
   паролей. Организация использует тариф Free; по действующей документации Supabase
   эта функция доступна только на Pro и выше. Включить её без смены тарифа нельзя.
8. Советник безопасности пометил `tochka_manage_access` и `tochka_visit`, потому
   что это SECURITY DEFINER-функции, доступные роли authenticated. Отдельный аудит
   подтвердил: anonymous-доступ отозван, search_path пустой, первая функция допускает
   управление только подтверждённому владельцу и запрещает удалить себя, вторая
   обновляет только запись текущего участника через auth.uid(). Их немедленный отзыв
   сломал бы управление доступом и облачный вход «Точки дня»; фактическая уязвимость
   не подтверждена.
9. Остаточный риск этих функций связан с компрометацией аккаунта владельца и с тем,
   что STUDKAB и «Точка дня» используют общий Auth-проект. Устранять его следует
   архитектурным разделением, а не отключением рабочих функций.
10. Автоматическая проверка подтверждает структуру и измеримые требования документа,
   но не заменяет предметную экспертизу исполнителя.

## 7. Решение о пилоте

Пилот нельзя считать начатым или завершённым автоматически. Для него необходимы
2–3 независимых тестовых пользователя, разные учётные записи и хотя бы два типа
устройств. До этого массовое подключение запрещено.

## Следующий этап

Подготовить закрытый пилот: три синтетические учётные записи, сценарии студента и
исполнителя, контрольные устройства, критерии остановки, журнал дефектов и план
безопасного удаления тестовых данных после завершения. Создание учётных записей
и отправка приглашений выполняются только отдельным подтверждённым действием.


## 8. Уточняющий аудит общей Supabase

Проверены точные определения, владельцы, search_path, ACL и места вызова функций.
`tochka_manage_access` вызывается Edge-функцией кабинета «Точки дня» для выдачи
и отзыва доступа; `tochka_visit` вызывается клиентом при облачном входе и фиксирует
посещение только участника с действующим доступом. Обе функции принадлежат postgres,
используют `SECURITY DEFINER SET search_path=''`, недоступны anon и разрешены только
authenticated/service_role. Код использует полностью квалифицированные таблицы.

Вывод: предупреждение советника — обоснованный повод для ручной проверки, но не
доказательство эксплуатации или ошибки. Текущие функции оставлены без изменения.
Безопасное будущее решение — отдельные проекты/Auth-контуры для STUDKAB и «Точки дня».
