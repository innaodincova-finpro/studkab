# Подготовка закрытого пилота STUDKAB

Дата проверки: 2026-09-13. Это подготовка и закрытая автоматическая проверка,
а не пилот с людьми и не подтверждение готовности для реальных студентов.

## Проверено без изменения рабочей базы

- В общем проекте Supabase зарегистрировано 5 учётных записей. Учётных записей
  с тестовыми доменами `example.test` или `example.com` нет.
- В `studkab_requests` находятся 4 записи; существующие записи не изменялись.
- Все таблицы STUDKAB в `public` имеют включённый RLS.
- Для `anon` и `authenticated` отсутствуют прямые табличные права на таблицы
  STUDKAB. Доступ приложения проходит через серверные Edge Functions.
- Функции очереди и выдачи доступны только `service_role` либо `postgres`.
- Размещены функции заявок, результата, генерации и уведомлений. Наличие функций
  не заменяет испытание двумя независимыми пользовательскими сессиями.

## Состав будущего пилота

Исполнитель продолжает работать под существующей подтверждённой учётной записью.
Создаются три новые синтетические учётные записи только с ролью студента:

| Маркер | Заявка | Назначение |
|---|---|---|
| `PILOT-STUDENT-A` | нефинансовая учебная работа | основной путь заявки и Word |
| `PILOT-STUDENT-B` | работа другой дисциплины | проверка изоляции и универсальности |
| `PILOT-STUDENT-C` | короткая тестовая работа | повторный вход, уведомление и смена аккаунта |

Администратора или куратора из этих аккаунтов не создаём: таких пользовательских
ролей нет в утверждённом MVP. Административные действия выполняет существующий
исполнитель. Все темы, имена, тексты и файлы должны иметь явную маркировку
`SYNTHETIC`; реальные персональные данные не используются.

## Проверки и критерии успеха

1. Каждый студент после входа видит только собственную заявку и собственный Word.
2. Прямая подстановка идентификатора чужой заявки получает отказ без раскрытия данных.
3. Сохранение переживает закрытие браузера и повторный вход.
4. Смена аккаунта не переносит локальный документ, статус или уведомление.
5. Исполнитель видит все три заявки, но выдаёт Word только исходному получателю.
6. Уведомление открывает правильную заявку после обязательного входа.
7. Проверенный Word скачивается побайтово в утверждённой версии; чужой или устаревший
   вариант блокируется.
8. После испытания состав тестовых данных сверяется по маркеру; удаление выполняется
   отдельной контролируемой операцией с предварительным перечнем объектов.

## Почему аккаунты пока не созданы

Создание Auth-пользователя — изменение рабочей общей базы. Для нормального входа
нужны три реально контролируемых тестовых адреса или иной согласованный способ
получения доступа. Адреса-заглушки не получают приглашения и не позволяют проверить
фактический путь пользователя. Прямая запись в `auth.users` через SQL запрещена:
она обходит штатный Auth API и может оставить некорректные связанные записи.

До создания аккаунтов также остаются обязательные предпилотные проверки из
`MVP_RELEASE_BASELINE.md`: восстановление резервной копии в отдельной среде,
проверка физических устройств, полного уведомления и нагрузки 15–20 студентов.

## Безопасный порядок продолжения

1. В отдельной тестовой среде восстановить резервную копию и подтвердить целостность.
2. Автоматически проверить нагрузочный сценарий 15–20 синтетических студентов.
3. Подготовить три контролируемых тестовых адреса и создать пользователей штатным
   Supabase Auth Admin API без автоматической внешней рассылки.
4. Создать три заявки с указанными маркерами и выполнить проверки изоляции.
5. Проверить iPhone и Android, затем уведомления и переход в заявку.
6. Только после успешных предпилотных проверок начать ограниченный пилот с людьми.

## Граница безопасности

Эта проверка была только читающей. Учётные записи, приглашения, заявки, уведомления,
данные, функции, настройки Auth и бюджет не изменялись. Отправка писем, Telegram и
платные вызовы не выполнялись.

## Закрытая автоматическая проверка

Тест `tests/pilot-isolation.test.mjs` создаёт в памяти три независимые сессии,
три заявки и три результата. Для каждой сессии проверяется собственный результат
и две попытки получить чужой. Чужая заявка возвращает одинаковое «не найдена»,
а чтение байтов чужого результата даже не начинается. Подмена `student_id` при
отправке игнорируется: сервер связывает заявку с подтверждённой сессией.

После смены всех трёх сессий повторный вход первого студента возвращает его прежний
результат. Исполнитель отдельно получает полный реестр трёх заявок. Проверка не
создаёт пользователей Auth и не обращается к рабочей базе или внешним каналам.

Фактический результат: полный локальный набор — 147/147 тестов, ошибок нет.
