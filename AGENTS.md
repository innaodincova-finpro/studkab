# Обязательная инструкция исполнителю STUDKAB

Перед любой правкой прочитать TASK.md, TRACEABILITY.md и CHANGE_CONTROL.md.
Они фиксируют уже согласованное задание. Не начинать новый цикл согласования.

## Ответственность
Пользователь определяет требуемый результат и рабочий сценарий. Исполнитель отвечает
за технические решения, интеграцию, сохранность данных и доказательства проверки.
Не соглашаться автоматически с технически неверным предложением: назвать конкретное
противоречие и предложить решение, сохраняющее цель пользователя.

## Четыре обязательных правила
1. Работать по единому TASK.md. Для каждого изменения указывать требование.
2. Соблюдать эту инструкцию: не менять цель, архитектуру и определения незаметно.
3. Вести TRACEABILITY.md: требование → код/версия → проверка → фактический результат
   → публикация. Без доказательств требование не закрыто.
4. До объединения выполнить CHANGE_CONTROL.md. Для незавершённой интеграции
   допустим draft PR, но недопустима отметка «исправлено в приложении».

## Запрет подмены результатов
- Прототип не равен исправлению действующего приложения.
- Локальные тесты и подставной провайдер не равны производственной приёмке.
- Публикация не равна доказательству работоспособности.
- Закрытие браузера не проверяет восстановление после остановки обработчика.
- Наличие очереди само по себе не доказывает сохранность, восстановление или отсутствие дублей.
- «Полный», «готовый», «проверенный» допустимы только при выполненных критериях TASK.md.
- План, код, тест, развёртывание и пользовательский результат — разные статусы.
- Историческая причина сбоя не установлена. Не представлять гипотезу или
  принудительную остановку в тесте как подтверждённую аварию пользовательского сервера.

## Инженерные границы
Использовать действующие Supabase/Postgres/Edge и Cloudflare, GitHub Pages.
Новый стек или инфраструктура требуют документированного обоснования до реализации;
прототип нельзя выдавать за производственную интеграцию.
Сохранять существующие данные и доступ. Не объединять открытые PR без проверки
зависимостей и совместимости. Не читать и не выводить секреты в журналы или чат.
Технические параметры восстановления и повторов определять самостоятельно.
Расходы — только в пределах ранее разрешённого бюджета; если числовой лимит
не установлен в проверяемой конфигурации, платный запуск не выполнять.
Новые платные услуги и превышение бюджета требуют разрешения пользователя.

## Корректировки
До изменения направления записать в CHANGE_CONTROL.md: требование, фактическое
основание, альтернативы, решение, влияние на данные/совместимость/бюджет,
проверку и откат. Рутинные решения в согласованных границах не требуют нового разрешения.
При блокировке одного шага продолжать независимую разрешённую работу.
Отчёт о ходе работы не подменяет выполнение.
