# Закрытая нагрузочная проверка STUDKAB

Дата: 2026-09-14. Контур: локальный Node и GitHub Safety, без рабочей базы.

## Сценарий

- 20 независимых синтетических студенческих сессий одновременно отправляют
  20 заявок с уникальными идентификаторами.
- Сервер связывает каждую заявку с подтверждённой сессией, игнорируя переданный
  клиентом чужой `student_id`.
- Все 20 студентов одновременно получают собственный результат.
- Каждый студент пытается открыть результат соседнего аккаунта.
- Создаются новые экземпляры сессий, имитирующие повторный вход, и все студенты
  повторно получают только собственный результат.
- Исполнитель получает полный реестр из 20 заявок.

## Критерии

1. Ровно 20 заявок, 20 уникальных идентификаторов и 20 владельцев.
2. Ни одна заявка не связана с переданным клиентом чужим владельцем.
3. Все 20 собственных результатов доступны.
4. Все 20 попыток получить чужой результат дают 404 до чтения результата.
5. После повторного входа доступны те же 20 собственных результатов.
6. В реестре исполнителя присутствуют все 20 заявок.

## Фактический результат

Все критерии выполнены. Полный локальный набор: 148/148 тестов, ошибок нет.
Окончательным доказательством публикации является зелёный GitHub Safety PR.

## Ограничение результата

Это проверка конкурентного поведения серверного обработчика с изолированным
хранилищем в памяти. Она не доказывает фактическую пропускную способность рабочей
Supabase, доставку уведомлений, поведение мобильной сети или вход настоящих Auth-
пользователей. Production, Auth, данные, Telegram, email, AI и бюджет не затронуты.
